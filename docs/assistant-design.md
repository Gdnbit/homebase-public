# HomeBase 内置助理：调研与实施约定

日期：2026-11-10。用户已授权调研、规划与实现，微信默认复用同一助理；默认模型按用户选择暂不启用。没有真实推理、收费模型验证或密钥迁移授权的扩大解释。

## 目标与验收

新增独立「AI 助理」页面，让用户选择已有模型渠道/凭据引用，通过自然语言发现能力、调用接口、查询任务和取得文件。桌面与微信共用会话引擎、模型适配、工具目录和执行策略；微信普通消息默认交给该引擎，已有明确指令保持兼容。

验收包括：模型未启用不产生推理请求；合成模型能够完成多个工具轮次；模型输出本身不能替代执行；重复消息/调用不重复写入；需要确认的实际操作在确认前不执行；取消与重启不重提已受理业务；两个入口调用同一实现；新媒体在隔离目录生成并通过既有附件路径返回。

## 现状核对

- 模型库已有受控 Key 解析、固定厂商端点、模型/渠道绑定、Chat Completions 与 Responses 调用。
- 控制器已有命令契约、授权分类、稳定 request-id、持久受理账本与 job 查询。继续作为业务执行权威，助理不另造 shell 或绕过接口。
- Studio 有写作对话和 Claude CLI/MCP 图片工具，但定位、固定模型与文件工作区不适合直接成为全系统通用代理。
- 微信已有本人绑定、加密游标与消息索引、显式指令、任务恢复和真实视频附件验证，可复用通道能力。

## 官方协议调研

[OpenRouter 客户端工具调用](https://openrouter.ai/docs/guides/features/tool-calling) 与 [OpenAI 函数调用](https://developers.openai.com/api/docs/guides/function-calling) 均把执行放在应用端：模型提出工具名和 JSON 参数，应用执行并带原调用编号返回结果，再继续模型请求。Chat Completions 的 tool_calls/tool_call_id 与 Responses 的 function_call/call_id/function_call_output 需要分别适配，不能混用消息结构。

[OpenRouter 路由](https://openrouter.ai/docs/guides/routing/provider-selection) 支持要求端点接受所需参数。助理对该渠道请求工具参数支持，不静默丢掉 tools 或在不支持时假称执行。模型元数据、Key 配置和实际工具能力/余额分别说明；本次不以参考目录宣称所有账号模型均验证通过。

[腾讯 iLink 协议](https://github.com/Tencent/openclaw-weixin/blob/main/docs/protocol_zh_CN.md) 把微信消息收发与模型推理解耦。由 HomeBase 将已验证的本人消息交给统一引擎，再用原会话上下文回复，Bot Token 不参与模型上下文。

## 方案比较与选择

| 方案 | 适配结果 |
| --- | --- |
| 扩大 Studio/Claude CLI 工作区 | 能复用部分聊天组件，但会保留固定 CLI/模型及文件型工作区耦合，新增通用执行面 |
| 再启动独立 Agent 框架服务 | 可提供通用循环，但增加进程、状态和授权同步；与当前 Rust 控制器及微信账本重叠 |
| Rust 内嵌共享助理核心 | 复用现有 HTTP、凭据、控制器、加密存储与任务协议；两个入口只做适配，本轮采用 |

上述选择是基于当前仓库的工程判断，不是对框架普遍优劣的结论。

## 实施范围

新增助理协议适配、会话/轮次/工具执行核心、Tauri/CLI 命令与聊天页面；修改微信转接、导航、契约和相关测试。复用现有 Markdown、查询缓存、模型库与文件校验。默认不启用模型，界面与微信明确提示该状态，已有无模型指令继续可用。

工具采用发现 → 描述 → 调用 → 查询模式，覆盖已注册可用业务接口；凭据明文、授权弹窗、助理自身配置/确认入口和未实现接口不开放给模型。基础只读状态及新建隔离视频可直接执行；私人内容读取、现有数据写入、发布、其他收费生成等操作先展示具体接口及参数供用户确认。模型和工具输出不能自批确认。

业务 job 继续由现有控制器管理。每个工具操作先持久记录稳定编号，再执行；取消只停止助理后续步骤，不把已有业务改成取消/恢复。进程重启把未完成轮次标记为待核对，不自动重放。工具循环、输出大小和上下文设上限，保留完整工具调用分组，避免截断后出现悬空 call ID。

聊天历史、私有参数与审批内容独立使用当前用户 DPAPI 加密，不写入 Web Storage。模型只接收本次需要的对话和已授权工具结果，Key 继续由后端即时解析。视频复用既有已安装运行时，每次生成独立 run 目录；媒体只能从已登记且经过路径/哈希验证的结果中返回。

## UI 与验证

页面按现有暖白、灰蓝、衬线标题风格设计，包含会话列表、消息、真实工具步骤、附件和模型设置；覆盖未启用、思考/执行、待确认、取消、失败与结果状态。设计图存于 `outputs/page-design/assistant/2026-11-10/`。

采用合成模型/本地 HTTP、临时加密状态与隔离任务验证核心，再跑 CLI 契约、页面交互及原生桌面构建。用户选择的默认关闭状态最后用真实运行中接口核对；不为验收启用真实推理，也不触碰现有真实密钥。

## 实施状态

已实现共享 Rust 引擎、Chat/Responses 工具适配、加密会话、真人确认、停止/重启边界、任务与附件、桌面页面及微信普通消息转接。界面事件在应用层只使相关缓存失效；活动轮次小范围更新，离页不启动读取轮询。相同消息提交失败后的重试保留原 request_id，避免首次新会话已受理但回执丢失造成重提。

初次实现的默认关闭验证见 原验证报告。后续用户明确授权修复来源并启用免费模型，当前真实调用与重启验证见 免费助理启用。具体接口与边界见 [助理说明](assistant.md)，实时配置仍以 assistant_config_get 为准。

后续长期个人助理的成熟框架选型见 Harness / SDK 调研。该报告提出隔离验证 Deep Agents / LangGraph 本地侧进程的方案，尚未安装、切换引擎或迁移现有会话；不把上游功能说明视为已适配。

2026-11-11 已完成 综合选型与最小机制验证：推荐本地 Deep Agents TS + LangGraph 1.x，Pydantic AI + Harness 为第一替代。候选包只安装到 F 盘隔离实验根，未接入当前生产助理；该报告取代早期排序，但不等于生产准入通过。

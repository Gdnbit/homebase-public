# 模型失败、有限重试与原任务恢复

桌面与微信共用同一助理引擎。模型推理的网络重试与业务工具的执行是两回事：重试推理不会重新提交已完成工具；已有业务操作继续沿用原 turn、工具身份、控制 request_id/job_id 和检查点结果。

## 如何判断失败

`assistant_turn_get` 可选返回 `model_failure`；成功模型轮次的 `model_diagnostics` 记录尝试次数、耗时和有限重试记录。控制 `jobs.get.error` 的 code 提供明确类别，details 使用同一脱敏结构。结构只含分类、连接细节枚举、HTTP 状态、Retry-After、尝试次数与毫秒耗时，不包含 URL、Header、Key、请求正文、服务商错误正文或模型隐含推理。

`model_outcome_unknown` 表示轮次已经停下，但原模型请求的结果仍待核对。`assistant_turn_get`、会话窗口的轮次摘要和微信任务状态提供该字段。停止后仍有这个标记时，桌面显示「核对原任务」，微信说明后续步骤已停和模型结果未确认。轮次保留原状态及原结果，当前正在等待回复的轮次不使用这个终态标记。

| 情况 | acceptance | 处理 |
| --- | --- | --- |
| 请求构造失败、DNS/连接/TLS 建立失败 | not_submitted | 请求尚未提交推理；TLS/构造错误不自动重试，其他连接失败可在限定场景内重试。 |
| 收到 HTTP 错误响应或明确的 JSON 错误 | rejected | 保留 HTTP 状态；限定的短暂 HTTP 失败可有限重试，其余停止。JSON 正文错误本轮不在网络层自动重试。 |
| 提交后超时、连接中断、响应读取中断或响应格式无效 | unknown | 不自动重试，保留原任务；不能把缺少结果解释为未执行。 |

previous 保留最多两次先前尝试的分类和状态；不会因最后一次失败覆盖前面的原因。HTTP 200 正文内的服务商错误单独记录 provider_status，http_status 仍为200，不把逻辑错误码伪装成真实 HTTP 状态。

常见 code：`MODEL_CONNECT_FAILED`、`MODEL_CONNECT_TIMEOUT`、`MODEL_RESPONSE_TIMEOUT`、`MODEL_TRANSPORT_UNKNOWN`、`MODEL_RESPONSE_INTERRUPTED`、`MODEL_RESPONSE_INVALID`、`MODEL_AUTH_REJECTED`、`MODEL_QUOTA_REJECTED`、`MODEL_RATE_LIMITED`、`MODEL_PROVIDER_UNAVAILABLE`、`MODEL_HTTP_REJECTED`。

脱敏模型失败会写入原控制操作账本的 model_failure，应用重启后可以按原 job_id 查询，不重新发起请求。普通业务返回和任意错误正文仍不持久化到此账本。旧版本没有保存的错误无法补造，旧记录仍保持原状态。

## 自动重试的边界

只对 OpenRouter 明确 `:free`、纯文本/客户端 function 工具推理生效；必须关闭 provider fallback、设置非空的全零 max_price，且没有输出目录、流式输出、图像输出或服务端工具。不会自动改用其他模型、其他 Key 或付费渠道。图片/音频/视频等创建操作不重试。

最多3次尝试。连接阶段上限20秒，单次请求最多90秒，整个网络重试过程受120秒总预算约束；响应读取沿用该次请求截止。实际退避受剩余预算限制。

- 明确 HTTP 408/429/500/502/503/504，或请求提交前连接失败，可在上述限定场景内重试。
- 优先遵守 Retry-After 秒数或 HTTP 日期，否则指数退避并增加小幅随机抖动。
- 服务商明确 `x-should-retry: false` 时停止；401/402/403、请求格式问题、TLS 异常等不自动重试。
- Retry-After 大于剩余预算时停止并保留等待提示，不提前请求，也不无限挂起任务。
- 停止任务会取消正在等待的宿主推理及退避，不继续发起下一次尝试；已有业务结果不伪装成撤销。

## 继续与恢复

明确拒绝或尚未提交的推理失败，不再误标成“受理未知”：失败分类持久化到原任务，`resumable=true` 且检查点有效时，可通过 `assistant_resume` 或微信“继续 <原任务编号>”继续。微信普通“继续”能否使用，由当前会话的控制路由与明确目标决定；不要对不明确的任务猜编号。

继续保留原任务与已完成步骤，从未完成的推理处接续；成功工具结果和模型结果按原身份复用。重复微信消息仍经原 message_id 去重，不新建业务任务。应用重启不会擅自恢复一个已明确失败的任务，需要一次明确继续。

开发中修复：继续不再清空工具失败计数，达到32种失败也不再轮换丢弃旧依据。台账以原192步骤预算为边界，满额明确停止新动作，旧依据保留；不解除其他历史/容量限制。此前已被旧版清掉的记录无法补造。

显式继续原Deep Agents任务后，被失败保护拦截的旧调用会向同一图返回 `status=failed`、`code=TOOL_RETRY_BLOCKED`、`executed=false`，让助理查询原job、修正缺失条件或选择其他方案。它没有执行，也不能作为成功或完成证据。同一继续代际、相同工具与参数只给一次这种反馈；模型只换调用编号原样再提时再次停止，避免空转。原失败步骤、计数、任务/控制编号保持，重建引擎不解除保护。改参数不自动形成授权，真实写入仍走原权限与确认。验收和部署状态见持续Goal，不能据源码存在推断日常程序已更新。

未知受理状态仍 `resumable=false`，重启、重复消息或继续请求都不能清除它；先查询原业务 job、产物和状态。进程在请求进行中退出时，不能仅根据“未保存响应”假定请求失败。此策略优先防止重复执行，不承诺跨外部服务的绝对 exactly-once。

CLI 等待超时或网络断开只代表调用方没拿到结果：继续查询原控制 job_id，不生成新的 request_id 重提。业务 status、文件与校验结果才是完成依据。

# 助理状态记录与快照

消息、轮次和任务的内部集合使用`Records<T>`，每项由标准库`Arc`持有。只读快照共享不可变记录；通过索引、`find_mut`或`matching_mut`修改时，由`Arc::make_mut`分离当前项。状态事务、权限、编号、保存和错误处理仍由原Engine负责，共享记录不是另一套任务状态。

`matching_mut`先用只读引用检查条件，再为匹配项取得可写记录。消息回填、旧任务恢复、进度刷新、投递和修改要求使用这一约定，避免为判断条件而复制全部历史。需要修改所有项时才使用全量可写迭代。

序列化仍是原来的JSON数组，保持顺序、字段和值，不增加磁盘格式版本或迁移。公开会话/轮次DTO、控制schema和CLI契约未改变。新旧快照之间的修改相互隔离；更新闭包拒绝或保存失败时，原State和已保存快照保持不变。

`Records<T>`减少内存快照的深拷贝。普通旧格式仍保存完整状态，沿用单会话 200 条消息和 100 个自有任务的接纳边界。显式隔离的 format3 容量模式支持完整闭合会话的不可变分段、按需读取和冷分区保存。

分段容量模式下，已完成并满足归档条件的轮次可将大型检查点、原模型结果与工具回执留在原加密记录。启动和冷会话重开逐条读取轮次，活跃状态保留步骤及查询所需的信息。原轮次的所有字段继续计入留存容量。仅更新设置时复用原加密分段，更新已压缩的轮次时从已核对的原记录补齐恢复字段。未完成或未知轮次保留运行恢复所需的完整字段。隔离验收

启动活跃会话时，先校验原分段，按保存顺序把轮次交给恢复逻辑。已在共享缓存的分段可以复用，新读的启动分段随恢复消费释放。显式档案读取继续复用共享缓存。进程实测

2026-11-18补充的局部记录提交是存储基础：调用方传入新鲜的全局Snapshot，并为指定series提供原位置引用、同编号更新和尾部追加；规范分段仍保存完整JSON记录。旧编号/顺序/来源、未覆盖记录及其他会话都必须保留，Context继续原滚动窗口规则。全保留的段零正文读取，必要混合段有界读取并沿原头原子发布；输入和待发布密文分别受64MiB上限约束。旧引用不是可对外提交的权限凭据或磁盘壳值。

容量实验模式的活跃会话现在通过此路径保存已完成的早期聊天消息。执行器保留轮次、任务、至少 48 条新消息和谈话上下文。附件及待恢复消息会形成保留边界。历史查询仍按完整顺序分页，任务进度仍使用原首条用户输入。磁盘沿用 format3 的完整记录，每次加密提交成功后才采用新的内存投影。验证与当前边界

容量模式的任务保存使用上一次成功发布的记录快照。正文未改的任务按原位置引用，修改和新增的任务正常编码。工作流证据、归属判定和产物读取继续使用完整的原任务。活跃会话仍在内存保留任务正文，存储字节预算仍检查完整历史。任务接纳与保存方案

实施与验收要求见阶段方案。长期存储设计继续遵循固定源码调研中的事务、原编号、在途保护和失败回滚要求。
